# Vendored FEEL evaluator

This directory is a fork of [`github.com/pbinitiative/feel`](https://github.com/pbinitiative/feel)
at **v1.0.6**, vendored under `pkg/feel/internal/` and renamed to package
`dialect`. It is licensed under the terms in `LICENSE`, which is reproduced here
unchanged.

Verdict embeds rather than imports it because the upstream evaluator has
defects that a DMN engine cannot paper over from the outside — they are in
unexported methods on upstream types, reached through upstream's own `Eval`
dispatch, so no amount of AST post-processing fixes them.

## Divergences from upstream

| Where | Upstream behaviour | Verdict behaviour | Why |
|---|---|---|---|
| `eval_binop.go` — `divOp`, `numeric.go` — `Div`, `IsZero` | `/` routed through `IntDiv`, so `1 / 3` evaluated to `0` and dividing by zero panicked in `math/big` | `/` is exact decimal division at the working precision; a zero divisor yields `null` | FEEL numbers are decimals (DMN 1.5 §10.3.2.3). Integer division makes every ratio, rate and proportion in a decision model silently wrong, and a panic in a rule engine is not a recoverable failure mode |
| `parser.go` — `parseName`, `keywordNamePrefixes` | A name absorbed *any* reserved keyword, so `x and y` parsed as one variable named `"x and y"` (evaluating to null with no error) and `if x then a else b` was a parse error | A keyword ends a name unless the result is still a prefix of `date and time`, `days and time duration` or `years and months duration` | FEEL names may contain spaces, and three standard built-ins embed `and`. Resolving the ambiguity in favour of names breaks conjunction, `in`, and every `if` with a variable condition — the three constructs Conformance Level 3 is built on |
| `eval_binop.go` — `compareInterfaces`, `instantOf` | Comparison matched only the `HasTime` interface, which `FEELDate` does not satisfy (it exposes `Date()`), so `date(...) < date(...)` raised a type error | Temporal comparison goes through `instantOf`, which handles all three FEEL temporal types and their mixtures | "Before the cutoff" and "older than 18" are the bread and butter of a decision table. A rule engine whose date comparisons raise is not usable for the models people actually write |
| `parser.go` — `singleElement`, `parseRangeOrArray`, `endpointExpression`, `delimited` | Only `(a..b)`, `[a..b]`, `(a..b]` and `[a..b)` parsed. `]a..b]` and `[a..b[` — the same intervals in the spec's other spelling — were syntax errors | All six bracket forms parse, with `]` opening an exclusive interval and `[` closing one | DMN 1.5 §10.3.1.7 admits both spellings, and modellers write both. A syntax error on a legal unary test rejects the whole model, and the message points at a bracket rather than at the choice of notation |
| `eval_binop.go` — `orderingOp`, `compareGTOp`, `compareGEOp`, `compareLTOp`, `compareLEOp` | `<`, `<=`, `>` and `>=` ordered null below every value, so `2 < null`, `null >= null` and `min([2]) < max([])` evaluated to `true` | An ordering comparison with a null operand yields `null`; `=` and `!=` are unchanged (`null = null` is `true`, `2 = null` is `false`) | DMN 1.5 §10.3.2: comparing an absent value is not a boolean question. A `true` there fires rules on missing data. Verdict's unary-test layer (`pkg/feel/unarytest.go`) treats the null outcome of a comparison test as "not satisfied" |
| `eval.go` — `quantify`, `SomeExpr.Eval`, `EveryExpr.Eval` | `some x in L satisfies P` returned the first element satisfying `P` (and leaked an interpreter scope doing so); `every` returned the list of elements satisfying `P` | Both yield a boolean. `some` is `true` if any `P` is `true`, else `null` if any `P` is null or non-boolean, else `false` (`false` over an empty list); `every` is `false` if any `P` is `false`, else `null` if any is null or non-boolean, else `true` (`true` over an empty list) | DMN 1.5 FEEL grammar rule 58: a quantified expression is a boolean. Returning an element makes `some ... and x` and a `true` input entry silently compare a number or list to a boolean, so the rule never fires |
| `eval_binop.go` — `inOp` | `null in [1..10]` ordered null below the start and evaluated to `false`, so `not(null in [1..10])` was `true` | Membership of a null value in a range yields `null`; membership in a list is unchanged (`null in [1, null]` is `true`) | DMN 1.5 §10.3.2: range membership is the conjunction of its endpoint comparisons, each null for a null operand — the same divergence as the row above, reached through `in`. Verdict's unary-test layer (`pkg/feel/unarytest.go`) applies it to a bare range entry (`[1..10]`), so `not([1..10])` does not match a null input |
| `parser.go` — `parseSomeOrEvery` | `some` and `every` accepted one iteration context; `some x in A, y in B satisfies P` was a syntax error at the comma | A comma-separated list of iteration contexts parses and desugars to nested quantifiers of the same kind, so the result is the three-valued fold of `quantify` over the cartesian product and a later context can reference an earlier name (`some x in A, y in x.items satisfies …`). Any empty context makes `some` false and `every` true | DMN 1.5 FEEL grammar rule 58 admits several iteration contexts, as rule 46 does for `for`, which the fork already parsed. A legal expression rejected at load forces modellers to rewrite it as nested quantifiers |
| `parser.go` — `parseForExpr`; `ast.go` — `ForExpr.Continues`; `eval.go` — `ForExpr.Eval` | `for x in A, y in B return e` parsed as nested `for`s and returned a list of lists, one inner list per element of `A` | Every context but the innermost is marked `Continues`, and its evaluation splices the inner context's list into its own, so the result is one flat list over the cartesian product in context order (`for x in [1,2], y in [3,4] return x * y` is `[3,4,6,8]`). A later context still sees earlier names. Only context nesting is flattened: a body that returns a list still yields a list of lists (`for x in [1,2] return [x]` is `[[1],[2]]`). The fork has no `partial`, so it is not affected. An integer-range context (`for i in 1..2, j in 1..i return j`) flattens the same way | DMN 1.5 FEEL grammar rule 46 and §10.3.2.14 define the multi-context `for` over the cartesian product with a single list result. The nested shape broke every downstream `count`, `sum` or comparison silently |
| `eval.go` — `quantify` | `some` and `every` over a value that is not a list (`some x in 5 satisfies x > 1`, or a scalar input variable) raised a type mismatch, so the evaluation failed | A non-list iteration domain is iterated as the one-element list holding it, in every iteration context of a quantifier. A `null` domain is the singleton `[null]`: the condition is evaluated once with the name bound to null, so `some x in null satisfies x > 1` is `null` and `some x in null satisfies x = null` is `true`. `for` applies the same conversion (see the `iterationDomain` row). A range value (`[1..3]`) is not a list either and is likewise wrapped, binding the name to the range itself: DMN 1.5 §10.3.2.14 iterates only a list or the two-expression integer form `1..3`, not a range value, so `some x in [1..3] satisfies 2 in x` is `true`. Write `some x in 1..3` to iterate the integers | DMN 1.5 implicit conversions (§10.3.2.9): a single value where a list is expected is converted to a singleton list. A modeller who writes a quantifier over an input that is sometimes a scalar gets an answer rather than a failed decision |
| `range_value.go` — `HasNullEndpoint`, `nullOnNullOperand`, `rangePrelude`; `eval_binop.go` — `inOp` | A range with a null endpoint ordered null below every value, so `[null..10]` behaved as "up to 10": `5 in [null..10]` was `true`, `5 in (5..null]` was `false`, and `before`, `after`, `meets`, `met by`, `overlaps`, `overlaps before`, `overlaps after`, `finishes`, `finished by`, `starts`, `started by`, `includes`, `during` and `coincides` answered booleans over it | Membership in a range with a null endpoint, and every range built-in given such a range as `a` or `b`, yields `null`. Verdict's unary-test layer treats a bare `[null..10]` entry as "not satisfied", so neither it nor `not([null..10])` matches | DMN 1.5 §10.3.2: membership and the §10.3.4 range functions are defined by endpoint comparisons, each null for a null operand. Read conservatively, since the spec does not give a literal null endpoint an "unbounded" meaning. The fork has no internal null-endpoint encoding to protect: `< 10` parses as a comparison, never a range, and the analyser probes through those same comparisons. A null *point* argument (`before(null, [1..10])`) is the next row |
| `range_value.go` — `nullOnNullOperand`, `rangePrelude` | A null `a` or `b` ordered null below every value, so `before(null, [1..10])` and `before(null, 5)` were `false`, `before(5, null)`, `after(null, 5)` and `after(null, [1..10])` were `true`, and `includes([1..10], null)`, `during(null, [1..10])`, `starts(null, [1..10])`, `started by([1..10], null)`, `finishes(null, [1..10])` and `finished by([1..10], null)` were `false`; `meets`, `met by`, `overlaps`, `overlaps before`, `overlaps after`, `coincides`, and `finishes(10, null)` raised a type mismatch instead | Every range built-in (`before`, `after`, `meets`, `met by`, `overlaps`, `overlaps before`, `overlaps after`, `finishes`, `finished by`, `includes`, `during`, `starts`, `started by`, `coincides`) yields `null` when `a` or `b` is null, whether that position takes a point or a range. This includes `coincides(null, null)`, which is `null`, not `true` | DMN 1.5 §10.3.4 defines each range function through ordering comparisons between points and endpoints, and §10.3.4's general rule makes a built-in given a parameter outside its domain null — null is not a point. The spec-literal reading of `coincides(point1, point2)` as `point1 = point2` would make `coincides(null, null)` `true` through FEEL's `null = null`; Verdict takes the domain rule instead, so all fourteen functions answer a null operand the same way. Two non-null points to `coincides` (`coincides(1, 1)`) still raise a type mismatch upstream; that is not a null-operand case and is not changed by this row |
| `eval_binop.go` — `typedOp`, `numberOp` | `+`, `-`, `*`, `/` (and the non-FEEL `%`) with a null operand, or with operand types the operator has no meaning for, raised a type mismatch, so `1 + null` failed the evaluation; and `+` concatenated a string with a number, so `1 + "a"` was `"1a"` | Arithmetic with a null operand, or over a type pair the operator is not defined for, yields `null`. `+` concatenates two strings only. Number arithmetic, string concatenation, date-and-time ± duration, date-and-time − date-and-time and division by zero (null) are unchanged | DMN 1.5 §10.3.2: arithmetic is defined only over the type pairs its semantic tables list, and is null otherwise — null operands included. A missing input in `a + b` is an absent answer (flagged `VERDICT_EVAL_004`), not a failed expression (`VERDICT_EVAL_005`). Spec-literal reading of mixed string/number `+`: null, though some engines concatenate |
| `parser.go` — `mulOrDivOp`, `powOp`, `negationOp`; `scan.go` — `**` token; `eval_binop.go` — `powOp`, `Negation`; `numeric.go` — `Pow` | Neither `**` nor unary `-` parsed: a leading minus was only ever part of a numeric literal, so `-x`, `-(a + b)` and `2 ** 3` were syntax errors | `**` binds tighter than `*`/`/` and associates left (`2 ** 3 ** 2` is `64`); unary `-` binds tighter than `**` (`-x ** 2` is `(-x) ** 2`, consistent with the literal `-2 ** 2` being `4`). Negation is defined over numbers and durations; `**` over numbers, exact for integer exponents up to 2^16 and through float64 otherwise. Any null operand, other type, or non-finite result (`0 ** -1`, `(-8) ** 0.5`, overflow) is `null` | DMN 1.5 grammar rules 4e and 4f make both part of the arithmetic every conformance level admits. The spec's grammar does not fix the associativity of `**` or its precedence against negation; the fork's left-associative binary-operator style and its literal `-2` were followed |
| `parser.go` — `UnexpectedToken.Error` | The message appended ten frames of the parser's own Go call stack | The message is the position and the expected tokens; the frames stay available through `Callers()` | The text surfaces to a modeller as a `VERDICT_LOAD_013` diagnostic about one cell of their decision table. Parser internals there bury the one line they can act on |
| `parser.go` — `iterationContext`; `ast.go` — `IterationRange`; `eval.go` — `IterationRange.Eval`, `iterationEndpoint`, `ForExpr.Eval`, `quantify` | An iteration context was a plain expression, so `for i in 1..3 return i` was a syntax error at the `..`, and `for i in [1..3]` (a range value) a type mismatch | `name in a..b` iterates the integers from `a` to `b` inclusive, ascending or descending (`1..3` is `[1,2,3]`, `3..1` is `[3,2,1]`, `2..2` is `[2]`), in every context of a `for`, `some` or `every`, composing with the multi-context forms (a later context may use an earlier name as an endpoint). Endpoints must be FEEL numbers with integral values that fit an int64; any other endpoint — a fraction, null, a string — makes the whole `for`/`some`/`every` null rather than raising a type mismatch (in a nested quantifier context that null folds three-valued). A range *value* such as `[1..3]` is not iterated: it is a singleton domain for `for`, `some` and `every` alike. The new node appears only inside `for`/`some`/`every`, which the S-FEEL gate already rejects | DMN 1.5 FEEL grammar rule 47 (`iteration context = expression, [ "..", expression ]`) and §10.3.2.14, which iterate only a list or two integer expressions joined by `..`; the spec defines no result for non-integer endpoints, so the general FEEL rule that an expression outside its semantic domain is null applies. **Deliberate extension:** grammar rule 58 gives `some`/`every` a plain expression, not an iteration context; the fork accepts `a..b` there as well (as the open OMG issue DMN17-107 proposes) because rejecting it would be the only place `a..b` is not a domain |
| `eval.go` — `iterationDomain`, `ForExpr.Eval`, `quantify` | `for` over a value that is not a list (`for x in 5 return x * 2`, a scalar input variable, or `null`) raised a type mismatch, so the evaluation failed | A non-list domain is iterated as the one-element list holding it, in every iteration context of a `for`, through the same helper the quantifiers use: `for x in 5 return x * 2` is `[10]`, `for x in null return x` is `[null]` (the body sees null, as a quantifier's condition does), and `for x in [1, 2], y in 3 return x * y` is `[3, 6]`. A range value is wrapped, not iterated: `for x in [1..3] return 2 in x` is `[true]`. An integer-range context (`1..3`) still iterates its integers, and one with a non-integer endpoint is still null rather than `[null]` | DMN 1.5 implicit conversions (§10.3.2.9): a single value where a list is expected is converted to a singleton list. Consistent with the quantifier row, so `for` and `some`/`every` agree on every domain |

The trade-off in the second row is that a model variable whose name contains a
reserved word (`Rent and Rates`) cannot be referenced unqualified. Every other
FEEL implementation makes the same trade.

The trade-off in the interval row is that `[` cannot be a list index in an
interval's upper endpoint, because there it is genuinely ambiguous with the
closing bracket: `[1..xs[1]]` does not parse. Parenthesise the endpoint —
`[1..(xs[1])]` — which is what `delimited` restores indexing for. Every other
position, including `xs[1]` on its own and `[1, 2, 3][1]`, is unaffected.

## Keeping the fork honest

The divergences above are the *only* intentional ones. When upstream fixes one
of these defects, the fix should be taken and this table shortened rather than
the fork growing. Everything Verdict adds on top of the standard library lives in
`pkg/feel/stdlib.go`, outside this directory, precisely so that the fork's diff
against upstream stays small enough to re-apply.
