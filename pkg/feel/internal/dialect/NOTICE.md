# Vendored FEEL evaluator

This directory is a fork of [`github.com/pbinitiative/feel`](https://github.com/pbinitiative/feel)
at **v1.0.6**, vendored under `pkg/feel/internal/` and renamed to package
`dialect`. It is licensed under the terms in `LICENSE`, which is reproduced here
unchanged.

Verdict embeds rather than imports it because the upstream evaluator has
defects that a DMN engine cannot paper over from the outside — they are in
unexported methods on upstream types, reached through upstream's own `Eval`
dispatch, so no amount of AST post-processing fixes them.

## Divergences from upstream

| Where | Upstream behaviour | Verdict behaviour | Why |
|---|---|---|---|
| `eval_binop.go` — `divOp`, `numeric.go` — `Div`, `IsZero` | `/` routed through `IntDiv`, so `1 / 3` evaluated to `0` and dividing by zero panicked in `math/big` | `/` is exact decimal division at the working precision; a zero divisor yields `null` | FEEL numbers are decimals (DMN 1.5 §10.3.2.3.1). Integer division makes every ratio, rate and proportion in a decision model silently wrong, and a panic in a rule engine is not a recoverable failure mode |
| `parser.go` — `parseName`, `keywordNamePrefixes` | A name absorbed *any* reserved keyword, so `x and y` parsed as one variable named `"x and y"` (evaluating to null with no error) and `if x then a else b` was a parse error | A keyword ends a name unless the result is still a prefix of `date and time`, `days and time duration` or `years and months duration` | FEEL names may contain spaces, and three standard built-ins embed `and`. Resolving the ambiguity in favour of names breaks conjunction, `in`, and every `if` with a variable condition — the three constructs Conformance Level 3 is built on |
| `eval_binop.go` — `compareInterfaces`, `instantOf` | Comparison matched only the `HasTime` interface, which `FEELDate` does not satisfy (it exposes `Date()`), so `date(...) < date(...)` raised a type error | Temporal comparison goes through `instantOf`, which handles all three FEEL temporal types and their mixtures | "Before the cutoff" and "older than 18" are the bread and butter of a decision table. A rule engine whose date comparisons raise is not usable for the models people actually write |
| `parser.go` — `singleElement`, `parseRangeOrArray`, `endpointExpression`, `delimited` | Only `(a..b)`, `[a..b]`, `(a..b]` and `[a..b)` parsed. `]a..b]` and `[a..b[` — the same intervals in the spec's other spelling — were syntax errors | All six bracket forms parse, with `]` opening an exclusive interval and `[` closing one | DMN 1.5 §10.3.1.2 (grammar rules 9 and 11) admits both spellings, and modellers write both. A syntax error on a legal unary test rejects the whole model, and the message points at a bracket rather than at the choice of notation |
| `eval_binop.go` — `orderingOp`, `compareGTOp`, `compareGEOp`, `compareLTOp`, `compareLEOp` | `<`, `<=`, `>` and `>=` ordered null below every value, so `2 < null`, `null >= null` and `min([2]) < max([])` evaluated to `true` | An ordering comparison with a null operand yields `null`; `=` and `!=` are unchanged (`null = null` is `true`, `2 = null` is `false`) | DMN 1.5 §10.3.2.15: comparing an absent value is not a boolean question. A `true` there fires rules on missing data. Verdict's unary-test layer (`pkg/feel/unarytest.go`) treats the null outcome of a comparison test as "not satisfied" |
| `eval.go` — `quantify`, `SomeExpr.Eval`, `EveryExpr.Eval` | `some x in L satisfies P` returned the first element satisfying `P` (and leaked an interpreter scope doing so); `every` returned the list of elements satisfying `P` | Both yield a boolean. `some` is `true` if any `P` is `true`, else `null` if any `P` is null or non-boolean, else `false` (`false` over an empty list); `every` is `false` if any `P` is `false`, else `null` if any is null or non-boolean, else `true` (`true` over an empty list) | DMN 1.5 FEEL grammar rule 46: a quantified expression is a boolean. Returning an element makes `some ... and x` and a `true` input entry silently compare a number or list to a boolean, so the rule never fires |
| `eval_binop.go` — `inOp` | `null in [1..10]` ordered null below the start and evaluated to `false`, so `not(null in [1..10])` was `true` | Membership of a null value in a range yields `null`; membership in a list is unchanged (`null in [1, null]` is `true`) | DMN 1.5 §10.3.2.15: range membership is the conjunction of its endpoint comparisons, each null for a null operand — the same divergence as the row above, reached through `in`. Verdict's unary-test layer (`pkg/feel/unarytest.go`) applies it to a bare range entry (`[1..10]`), so `not([1..10])` does not match a null input |
| `parser.go` — `parseSomeOrEvery` | `some` and `every` accepted one iteration context; `some x in A, y in B satisfies P` was a syntax error at the comma | A comma-separated list of iteration contexts parses and desugars to nested quantifiers of the same kind, so the result is the three-valued fold of `quantify` over the cartesian product and a later context can reference an earlier name (`some x in A, y in x.items satisfies …`). Any empty context makes `some` false and `every` true | DMN 1.5 FEEL grammar rule 46 admits several iteration contexts, as rule 44 does for `for`, which the fork already parsed. A legal expression rejected at load forces modellers to rewrite it as nested quantifiers |
| `parser.go` — `parseForExpr`; `ast.go` — `ForExpr.Continues`; `eval.go` — `ForExpr.Eval` | `for x in A, y in B return e` parsed as nested `for`s and returned a list of lists, one inner list per element of `A` | Every context but the innermost is marked `Continues`, and its evaluation splices the inner context's list into its own, so the result is one flat list over the cartesian product in context order (`for x in [1,2], y in [3,4] return x * y` is `[3,4,6,8]`). A later context still sees earlier names. Only context nesting is flattened: a body that returns a list still yields a list of lists (`for x in [1,2] return [x]` is `[[1],[2]]`). The fork has no `partial`, so it is not affected. An integer-range context (`for i in 1..2, j in 1..i return j`) flattens the same way | DMN 1.5 FEEL grammar rule 44 and §10.3.2.14 define the multi-context `for` over the cartesian product with a single list result. The nested shape broke every downstream `count`, `sum` or comparison silently |
| `eval.go` — `quantify` | `some` and `every` over a value that is not a list (`some x in 5 satisfies x > 1`, or a scalar input variable) raised a type mismatch, so the evaluation failed | A non-list iteration domain is iterated as the one-element list holding it, in every iteration context of a quantifier. A `null` domain is the singleton `[null]`: the condition is evaluated once with the name bound to null, so `some x in null satisfies x > 1` is `null` and `some x in null satisfies x = null` is `true`. `for` applies the same conversion (see the `iterationDomain` row). A range value (`[1..3]`) is not a list either and is likewise wrapped, binding the name to the range itself: DMN 1.5 §10.3.2.14 iterates only a list or the two-expression integer form `1..3`, not a range value, so `some x in [1..3] satisfies 2 in x` is `true`. Write `some x in 1..3` to iterate the integers | DMN 1.5 implicit conversions (§10.3.2.9.4): a single value where a list is expected is converted to a singleton list. A modeller who writes a quantifier over an input that is sometimes a scalar gets an answer rather than a failed decision |
| `range_value.go` — `HasNullEndpoint`, `nullOnNullOperand`, `rangePrelude`; `eval_binop.go` — `inOp` | A range with a null endpoint ordered null below every value, so `[null..10]` behaved as "up to 10": `5 in [null..10]` was `true`, `5 in (5..null]` was `false`, and `before`, `after`, `meets`, `met by`, `overlaps`, `overlaps before`, `overlaps after`, `finishes`, `finished by`, `starts`, `started by`, `includes`, `during` and `coincides` answered booleans over it | Membership in a range with a null endpoint, and every range built-in given such a range as `a` or `b`, yields `null`. Read conservatively, since the spec does not give a literal null endpoint an "unbounded" meaning. The fork has no internal null-endpoint encoding to protect: `< 10` parses as a comparison, never a range, and the analyser probes through those same comparisons. A null *point* argument (`before(null, [1..10])`) is the next row |

Two non-null points to `coincides` are the `coincides` row below |
| `range_value.go` — `coincides` | Arguments were decoded into range structs with mapstructure, which turned a number (itself a struct) into a zero range, so `coincides(1, 1)`, `coincides(1, 2)` and two dates raised "bad type in comparation, <nil> vs. <nil>"; a point paired with a range raised a type mismatch | `coincides` dispatches on the argument types: two points are compared as `=` compares them (`coincides(1, 1)` is `true`, `coincides(1, 2)` `false`, dates and strings likewise), two ranges are equal when both endpoints and both closednesses are (`coincides([1..5], (1..5])` is `false`), and a point paired with a range (`coincides(1, [1..1])`) is `null`. The trade-off in the second row is that a model variable whose name contains a
reserved word (`Rent and Rates`) cannot be referenced unqualified. Every other
FEEL implementation makes the same trade.

The trade-off in the interval row is that `[` cannot be a list index in an
interval's upper endpoint, because there it is genuinely ambiguous with the
closing bracket: `[1..xs[1]]` does not parse. Parenthesise the endpoint —
`[1..(xs[1])]` — which is what `delimited` restores indexing for. Every other
position, including `xs[1]` on its own and `[1, 2, 3][1]`, is unaffected.

## Keeping the fork honest

The divergences above are the *only* intentional ones. When upstream fixes one
of these defects, the fix should be taken and this table shortened rather than
the fork growing. Everything Verdict adds on top of the standard library lives in
`pkg/feel/stdlib.go`, outside this directory, precisely so that the fork's diff
against upstream stays small enough to re-apply.
